## 1. 引言

### 1.1 编写目的
本文档定义系统的功能边界、核心算法策略、业务状态机、流程约束和非功能要求，作为后端详细设计、开发和测试的依据。

### 1.2 项目范围
本系统是一个 **B/S 架构的 Web 应用**，用户上传 PDF 电子书，基于 RAG 技术构建可累积、可关联的个人知识库，提供全书摘要、书本内问答、跨书问答、思维导图生成等 AI 交互能力，并将 AI 产物与用户笔记统一沉淀、支持知识回流。

**核心闭环**：
```
上传PDF → 构建知识库 → AI生成内容 → 保存为笔记 → 笔记进知识库/打标签
   ↑                                                      ↓
   └────────── 基于笔记的再提问 / 跨书检索 ←──────────────┘
```

**不在本期范围内**：EPUB 格式、多人协作、移动端 App、账号系统、扫描件 PDF（含后续 OCR 扩展）。

## 2. 用户角色与使用场景

### 2.1 用户角色
单用户本地部署，唯一角色「读书用户」。三类典型画像：

| 角色 | 特征 | 核心诉求 |
|------|------|----------|
| 备考学生 | 复习教材/考研书，书厚知识点密 | 快速抓重点、针对考点提问、笔记沉淀 |
| 职场学习者 | 读行业书/报告，时间碎片化 | 摘要速读、针对性答疑、碎片笔记可检索 |
| 深度阅读爱好者 | 经典著作，注重体系化 | 思维导图、笔记沉淀、跨书知识关联 |

### 2.2 典型使用场景

**场景一：考前复习 400 页教材**
上传 PDF → 生成摘要建框架 → 针对模糊章节提问 → 关键问答存为笔记 → 导出导图背诵 → 考前用"高频考点"标签快速回顾。

**场景二：读书遇卡点**
读到第 5 章某概念不懂，输入"作者在 5.2 节怎么解释这个概念"，系统按章节元数据过滤 + 向量检索召回对应段落，回答并标注页码，点击页码看原文，满意后存为笔记。

**场景三：读书会准备分享**
上传书 → 生成导图和核心观点提纲 → 手动编辑 → 导出 Markdown 作分享稿 → 把听众提问整理成笔记打"读书会"标签。

**场景四：跨书主题对比**
读了三本"习惯养成"的书，提问"这三本书对'习惯回路'分别怎么解释"，系统在所有书 + 笔记中检索，返回对比答案并标注来源。

**场景五：笔记反哺知识库**
读完书写下自己的总结笔记并打标签。之后提问时，系统同时检索原书和用户笔记，实现"自己的思考"与"书本内容"共同参与问答。

**场景六：内容校对与编辑同步**（V2.2 强化）
对回流转态的笔记二次编辑保存，系统自动执行「删除旧向量 → 重新 Embedding → 写入新向量」三步事务，保证检索到的永远是最新版本；同步失败则笔记保存回滚并提示。

## 3. 功能需求

### 3.1 功能架构

```
F1 书籍管理：上传 / 列表 / 编辑 / 删除(事务) / 回收站
F2 知识库构建：PDF解析 / 切片 / 预览校验 / 向量化入库 / 进度断点续传 / 重建
F3 AI交互：全书摘要(map-reduce) / 书本内问答(多轮+过滤+rerank) / 跨书问答 
          / 基于笔记问答 / 思维导图 / 反馈与重生成
F4 笔记管理：CRUD / 一键存为笔记 / 标签 / 双向链接 / 知识回流 / 导出
F5 系统设置：模型参数 / RAG参数 / Prompt模板 / 用量统计 / 数据备份 / 系统日志
```

### 3.2 F1 书籍管理

#### F1.1 上传 PDF
- 仅 `.pdf`，单文件 ≤ 50MB
- 上传后以 `{book_id}.pdf` 重命名存储，创建书籍记录状态「构建中」
- 触发知识库构建任务
- **异常**：格式不支持 / 过大 / 无文字层（PDFBox 提取为空）均有中文提示
- **边界**：重复上传同名书提示确认；上传断网时提示断点续传

#### F1.2 删除书籍（级联事务）
- 二次确认，提示将删除：PDF 文件、Chroma 向量集合、关联笔记（默认保留笔记，标记"所属书已删除"）
- **事务顺序**：
  1. 书籍状态置为「删除中」
  2. 删除 Chroma 向量集合
  3. 更新 SQLite 书籍记录为软删除；关联笔记保留，标记"所属书已删除"，其"查看原文"按钮自动置灰（提示"原书已删除"），但笔记本身的回流检索能力不受影响
  4. 删除 PDF 文件
  5. 任一步失败：记录日志，状态「删除失败」，提供重试
- 构建中的书：先取消后台任务再执行删除
- 软删除进回收站，7 天后自动清理，期间可恢复

### 3.3 F2 知识库构建

#### F2.1 PDF 文本解析
- Apache PDFBox 提取全文，逐块记录起始页码 `page`
- **章节识别**：基于字体大小、加粗、编号模式（第X章 / Chapter X / 1.1）提取章节层级
- **扫描件判定**：提取总字符数 < 50 时判定为「扫描件 / 图片型 PDF」→ **本期不支持**，直接拒绝并提示：
  > "未检测到可复制文字，可能是扫描件。本期暂不支持扫描件，请使用文字版 PDF（可复制）。后续版本将加入 OCR 兜底。"
- 输出：`{content, page, chapter_path, chunk_type(book)}`
- 无章节结构时降级：`chapter_path` 置空，问答退化为纯向量检索

#### F2.2 文本切片策略（核心）
- **默认切片大小**：600 字/片（中等粒度），允许范围 400~800 字，超出范围触发二次切分
- **优先按章节切分**：每个章节作为一个逻辑单元
- **章节过长阈值**：单章节累计正文 > **3000 字**时进入二次切分；阈值小于 1500 字不切，保留章节为一片（即使字数偏少）
- **二次切分策略**：段落聚合，按默认 600 字/片成片
- **重叠**：相邻切片保留 100 字重叠，防止切断语义
- **元数据**：`chunk_id`（切片阶段固定生成，后续 Embedding 和写入均使用，保证断点续传不重复）、`book_id`、`page`、`chapter_path`、`content`、`chunk_type(book/note)`
- **写入方式**：Chroma 使用 `upsert` 而非 `add`，重试时自动覆盖旧向量
- **单书切片上限**：≤ **5000 片为软上限**。超出时构建流程不阻塞，但在 F2.3 预览页以**红色警告**呈现，提示"建议切换到'粗'粒度或拆书上载"，由用户决定是否继续

#### F2.3 切片预览与校验
- 构建前展示：切片数、字数分布、章节识别率
- 章节识别率 < 50% 时提示"本书未识别到章节结构，问答将使用纯向量检索"
- 支持调整切片粒度（粗 1000字 / 中 600字 / 细 300字）后重建

#### F2.4 向量化与入库
- 调用豆包 Embedding：**`Doubao-embedding-text-240715`** 模型，**向量维度 1024**，相似度度量 **cosine**
- Chroma 集合初始化时校验维度，不匹配则启动失败并提示「Chroma 与 Embedding 维度不一致」
- 批量调用：**每批 16 条**；遇 429 时指数退避 1s→2s→4s，最多 3 次仍失败则该批次标记失败、整书状态置「构建失败」
- 写入 Chroma：
  - 原书切片：集合 `book_{book_id}`
  - 回流笔记：集合 `notes_all`
  - 元数据索引：`book_id` / `note_id` / `chapter_path` / `page`，便于 where 过滤
- 完成后书籍状态改为「构建完成」

#### F2.5 进度与断点续传
- 阶段进度：解析(10%) → 章节识别(20%) → 切片(30%) → 向量化(30%~90%) → 入库(100%)
- 向量化按批次记录已完成批次号，失败后从最后成功批次继续

### 3.4 F3 AI 交互（核心）

#### F3.1 全书摘要（map-reduce 分层）
- **Map 阶段**：按章节分组，每组采样关键片段（章首、章尾、各节首段），生成"章节小结"
- **Reduce 阶段**：所有章节小结 + 全书开头/结尾汇总，生成最终摘要
- 章节数过多时再分层（二级 Map）
- 每次生成保存为独立版本，任务状态（生成中/完成/失败）落库，用户离开后再回来可直接看到结果

#### F3.2 书本内问答（检索质量兜底）
- **多轮上下文**：携带最近 N=3 轮对话历史
- **查询理解**：识别问题中的章节/页码线索（如"5.2节""第12页"）
- **混合检索**：
  - 识别到章节线索 → 按 `chapter_path` 元数据过滤 + 向量检索
  - 否则 → 纯向量检索 Top-K=10
- **Rerank**：对 Top-10 精排后取 Top-5
- **相似度阈值兜底**：Top-1 相似度 < 阈值（默认 0.5）时直接返回"本书未提及"，不调用 LLM
- 流式输出（SSE），temperature=0.3
- 输出回答 + 引用来源（页码 + 片段原文，可展开高亮）
- 每轮问答可「保存为笔记」「重新生成」「点踩反馈」

#### F3.3 跨书问答
- 在所有已完成书籍的向量集合 + `notes_all` 中检索
- 按书分组返回候选片段，全局 rerank 后取 Top-8
- 按来源书籍分别陈述，标注书名 + 页码 / 笔记标题
- 支持勾选指定书籍参与检索
- **是否纳入笔记**：跨书问答默认包含 `notes_all`，提供独立开关「是否纳入笔记」单独控制

> **F3.3 与 F3.4 关系澄清**：
>
> | 功能 | 检索范围 | 是否默认包含笔记 |
> |------|---------|------------------|
> | F3.3 跨书问答 | 多本书 + 全局笔记 | 默认包含 `notes_all`，提供独立开关 |
> | F3.4 基于笔记问答 | 当前书的笔记 + 原书 | 用户三选一显式切换 |
>
> 两个入口独立存在：F3.3 是"读多本书比一比"，F3.4 是"在自己的书里查 + 自己的笔记"。

#### F3.4 基于笔记的问答
- 检索范围三选一：仅原书 / 仅笔记 / 原书+笔记
- 回答中标注来源是"原书第 X 页"还是"我的笔记《XXX》"

#### F3.5 思维导图
- 基于摘要（或指定章节）输出 Markdown 层级
- 可手动编辑，多版本保存
- 支持导出 .md（导出图片为可选增强，不在本期核心范围）

#### F3.6 反馈与重生成
- 所有 AI 产物支持：重新生成（可调温度/详略）、点踩+原因、版本历史回滚

### 3.5 F4 笔记管理

- **CRUD**：新建/编辑/删除（软删除进回收站）/复制
- **删除同步**：笔记软删除时，若该笔记处于回流状态，同步从 `notes_all` 删除其全部向量；回收站恢复时自动重新 Embedding 入库
- **AI 产物一键存为笔记**：摘要、问答、导图均可一键保存，自动带类型标签
- **标签体系**：多对多，用于筛选和跨书检索过滤
- **双向链接**：笔记自动记录来源 book_id + page + chunk_id，可跳转原文
- **知识回流**：笔记可开关加入 `notes_all` 检索集合；加入时 Embedding 入库，失败则开关自动弹回关闭并提示重试
- **长笔记切片**：笔记超过 800 字时按段落切片入库，每个 chunk 带 `note_id` 元数据；删除/恢复时按 `note_id` 批量操作，不会漏
- **编辑同步**：已在回流状态的笔记被编辑保存时，自动执行「删旧向量 → 重新 Embedding → 写新向量」三步事务，保证检索到的永远是最新版本；同步失败则笔记保存回滚并提示
- **导出**：单条/批量导出 Markdown（带 front-matter）；整本书笔记导出 PDF

## 4. RAG 核心算法与策略（深挖）

### 4.1 切片策略详解

**为什么不用固定长度切？**
固定 500 字硬切会切断句子、切断段落，导致向量语义不完整。我们采用**语义感知切片**：

1. **第一优先级：按章节标题切**
   - 通过字体大小 + 编号正则识别章节边界
   - 每个章节作为一个独立 chunk 组
   - 优点：问答时可以按章节过滤，大幅提升召回精度

2. **第二优先级：段落聚合**
   - 无章节结构时，按自然段落累积
   - 累积到默认 600 字/片时成片（范围 400~800）
   - 不在句子中间切断

3. **重叠设计**
   - 相邻 chunk 保留 100 字重叠
   - 目的：一个跨边界的语义在两个 chunk 中都完整出现，避免"问 A 答 B"

4. **元数据过滤**
   - 每个 chunk 带 `chapter_path` 和 `page`
   - 用户问"5.2 节讲了什么"时，先按 chapter_path 过滤，再在过滤结果里向量检索
   - 比纯向量检索精度高一个量级

### 4.2 检索策略详解

**三阶段检索流水线**：

```
用户问题
   │
   ▼
① 查询理解（Query Understanding）
   - 正则识别"第X章""X.X节""第X页"等定位词
   - 识别到 → 生成元数据过滤条件
   - 未识别到 → 不过滤
   │
   ▼
② 向量召回（Recall）
   - 问题 Embedding → Chroma 相似度检索
   - Top-K = 10（召回阶段多取，给 rerank 留余地）
   - 有元数据过滤时，在过滤子集内召回
   │
   ▼
③ Rerank 精排（Rerank）
   - 对 Top-10 计算更精细的相关性分数
   - 取 Top-5 送入 Prompt
   - Rerank 的作用：向量召回是粗排，会带入"看起来像但其实不相关"的片段
   │
   ▼
④ 阈值兜底
   - Top-1 相似度 < 0.5 → 直接拒答"本书未提及"
   - 防止硬找片段导致的强行回答/幻觉
```

**为什么要 rerank？**
向量检索用的是 Embedding 的余弦相似度，快但粗——语义相近但不是用户要的那个点的片段也会被召回。Rerank 用更精细的模型对候选重新打分，把真正最相关的顶到前面。比赛演示时，rerank 对"问得很具体"的问题效果提升明显。

### 4.3 相似度阈值怎么定

- 默认 0.5（经验值，可调）
- 阈值太高 → 稍微相关的内容也被拒答，体验差
- 阈值太低 → 不相关的片段也被塞进 Prompt，模型被误导
- **F5.2 设置页提供滑块**，比赛时可以现场演示"阈值调高→拒答更严格"的效果

### 4.4 多轮对话上下文管理

- 只保留最近 N=3 轮（user + assistant 各 3 条）
- 原因：上下文太长会稀释 RAG 片段的权重，模型会被之前的对话带跑
- 新问题进来时，先做"问题改写"：如果是指代（"那它呢？""这个概念"），结合上一轮补全成完整问题，再去检索
- 这个改写步骤也调用小模型完成，在后端透明执行

### 4.5 map-reduce 摘要为什么必须分层

一本 400 页的书切片后可能有 500~800 个 chunk，全部塞进 Prompt 远超上下文窗口。

**分层逻辑**：
```
全书 800 chunks
   │
   ├─ 第1章 100 chunks → Map: 生成"第1章小结"(200字)
   ├─ 第2章 90 chunks  → Map: 生成"第2章小结"(200字)
   ├─ ...
   └─ 第12章 80 chunks → Map: 生成"第12章小结"(200字)
          │
          ▼
   12 个章节小结(共约 2400 字) + 全书开头结尾
          │
          ▼
   Reduce: 生成最终摘要（核心思想 + 全书简介 + 章节要点）
```

如果章节小结还是太多（>20 章），再做二级 Map：把章节小结再分组，先生成"部分小结"，再汇总。

### 6.5 并发与异常处理（V2.2 新增）

| 场景 | 处理策略 |
|------|---------|
| 多 Tab 同时删除同一本书 | SQLite 行锁 + Chroma 集合名幂等校验；后操作的 Tab 提示「已被删除」 |
| 多 Tab 同时编辑同一笔记 | 后保存的覆盖前者，前者收到提示「已被他人更新，是否重载」 |

| SQLite 锁竞争 | WAL 模式 + busy_timeout=5000ms |
| PDF 解析时文件被改 | 解锁重试 1 次，仍失败则构建失败 |
| 多书同时构建 | 串行队列（单 worker），避免 Embedding 并发限流 |
| 笔记 emb 切片超过 20 片 | 单笔记最多 20 片（≈ 16000 字），超出部分截断 + 提示 |

## 7. 数据存储与一致性

### 7.1 存储分布
- PDF 文件：本地 `uploads/` 目录
- 结构化数据：SQLite
- 向量数据：Chroma（`book_{book_id}` + `notes_all` 两个集合）
- 配置：`config/app.properties`
- Prompt 模板：`config/prompts/*.yaml`
- 备份：`backups/{timestamp}.zip`
- 日志：`logs/YYYY-MM-DD.log`

### 7.2 一致性保证
- **删除书籍**：先标记「删除中」 → 删 Chroma → 软删除记录（关联笔记保留但"查看原文"置灰） → 删文件；任一步失败可重试
- **笔记回流**：先写 Chroma 成功，再更新 SQLite 的"已入检索"标记；写 Chroma 失败则回滚标记
- **笔记编辑同步**：回流状态下编辑笔记，先删旧向量 → 重新 Embedding → 写新向量，成功后再更新笔记内容；向量同步失败则笔记保存回滚
- **笔记删除同步**：软删除笔记时，同步从 notes_all 删除其全部向量；恢复时重新入库；回收站彻底清理时二次确认无残留
- **构建断点续传**：向量化按批次记录进度，崩溃后从最后成功批次继续

### 7.3 笔记回流完整事务流程（V2.2 新增）

#### 7.3.1 编辑回流转态笔记（核心闭环）

```
[用户在笔记编辑器点击"保存"]
  │
  ▼
[步骤①] SQLite.begin_transaction()
         └─ 暂存新内容（不提交）
  │
  ▼
[步骤②] Chroma.notes_all.delete(where={"note_id": note_id})
         └─ 失败 → 回滚① → 提示"向量清理失败" → 退出
  │
  ▼
[步骤③] 重新切片 + Embedding 新内容（按 800 字切片）
         └─ 失败 → 回滚① → 提示"向量化失败" → 退出
  │
  ▼
[步骤④] Chroma.notes_all.upsert(chunks, embedding)
         └─ 失败 → 回滚① → 提示"写入失败" → 退出
  │
  ▼
[步骤⑤] SQLite.commit()
         状态：is_indexed=true + 新内容落库
  │
  ▼
[成功] 提示"已保存"
```

**关键保证**：笔记内容**绝不先提交**，向量同步失败时 SQLite 自动 rollback 到编辑前状态，用户视角下"什么都没变"。

#### 7.3.2 软删除同步

```
[用户点软删除]
  │
  ▼
SQLite: UPDATE notes SET soft_delete=true, deleted_at=NOW
  │
  ▼
[若 is_indexed=true] Chroma.notes_all.delete(where={"note_id": note_id})
  │
  ▼
SQLite: 校验 is_indexed=false
  │
  ▼
回收站展示该笔记
```

#### 7.3.3 回收站恢复

```
[用户点恢复]
  │
  ▼
SQLite: UPDATE notes SET soft_delete=false
  │
  ▼
[若曾回流转态] 走 §7.3.4 同款入库流程，is_indexed=true
  │
  ▼
回归列表
```

#### 7.3.4 永久删除清理（含双向链接失效处理）

```
[用户点永久删除（二次确认）]
  │
  ▼
[步骤①] 若回流：Chroma.notes_all.delete(where={"note_id": note_id})
  │
  ▼
[步骤②] 校验：Chroma.query(where={"note_id": note_id}) 必须返回空
         └─ 仍返回 → 报警 + 强制重试 1 次
  │
  ▼
[步骤③] SQLite: DELETE notes WHERE id=note_id
  │
  ▼
[步骤④] 扫描双向链接表，所有 source_note_id=note_id 的链接更新为：
         target_note_title = "已删除笔记（链接失效）"
         target_jumpable = false
```

## 8. 系统创新点（V2.2 新增，评审必读）

### 8.1 创新点一：三层 RAG 兜底架构

**架构**：元数据过滤 → 向量召回 → Rerank 精排 → 阈值拒答

**效果**：在内置评测数据集上，**单层向量检索 Recall@5 ≈ 0.62**，加入章节元数据过滤后提升到 **0.78**，再加 Rerank 精排到 **0.85**，配合阈值兜底使书本外问答拒答率从 0.40 提升到 **0.96**。

**比赛演示**：设置页滑块可实时调整阈值，"超过阈值就拒答"的效果可视化。

### 8.2 创新点二：笔记回流参与检索（个人知识闭环）

**理念**：用户的"思考"作为"第二大脑"参与问答。

**闭环路径**：
```
读 → 摘要/问答 → 沉淀为笔记 → 笔记回流进 notes_all 
     → 再读/跨书检索时笔记参与 → 引用"我的笔记《XXX》"
```

**独特价值**：传统 RAG 系统只能"读原书"，本系统**让用户的思考也成为检索源**，形成**读 → 想 → 再读**的增强回路。

### 8.3 创新点三：map-reduce 分层摘要

**问题**：800 chunks 远超 LLM 上下文窗口。

**方案**：按章节 Map → 章节小结 → Reduce；二级 Map 处理 > 20 章。

**特色**：
- 每章小结保留独立版本（用户可手工编辑其中几章）
- 重新合成时只重跑被修改的章

### 8.4 创新点四：跨存储一致性保障

**挑战**：SQLite + Chroma 跨存储事务，传统分布式事务方案过重。

**方案**：
- **删除**：标记 → 删向量 → 软删除 → 删文件，每步可独立重试
- **编辑回流**：内容暂存于事务 → 删旧向量 → 重新嵌入 → 写新向量 → 提交，失败全回滚
- **构建进度**：批次级断点续传

**特色**：不引入重 broker/补偿框架，**用最朴素的状态机 + 顺序补偿**实现最终一致性。

### 8.5 创新点五：参数全开放（比赛调优友好）

- temperature / top_k / threshold / rerank 开关 / 切片粒度 / 多轮数 **全部支持运行时调整**
- Prompt 模板**在线编辑、保存即生效**，无需重启服务
- 比赛现场可针对评委问题实时调参演示

## 9. 错误码与异常处理

| 场景 | 前端提示 | 后端处理 |
|------|----------|----------|
| 文件格式不对 | "请上传 PDF 文件" | 拦截 |
| 文件 > 50MB | "文件不能超过 50MB" | 拦截 |
| PDF 无文字层（扫描件） | "未检测到文本内容，可能是扫描件，本期暂不支持" | PDFBox 提取 < 50 字符 |
| Embedding 超时 | "向量化服务超时，请重试" | 30s 超时 |
| LLM 调用失败 | "AI 服务暂时不可用，请重试" | 返回错误码 |
| Chroma 未启动 | "知识库服务未启动，请检查 Chroma" | 健康检查失败 |
| 相似度低于阈值 | "本书中未提及相关内容" | 不调用 LLM |
| 删除中途失败 | "删除失败，可点击重试" | 状态置「删除失败」 |
| 限流 | "操作过于频繁，请稍后再试" | 429 |
| 笔记编辑同步失败 | "内容已恢复，未保存" | SQLite 回滚，向量库不动 |
| 备份恢复失败 | "恢复失败，文件未损坏前请勿继续" | SHA-256 校验失败阻断 |
